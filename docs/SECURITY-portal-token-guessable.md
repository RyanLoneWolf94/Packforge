# Security: client portal tokens are guessable

**Severity:** High (client confidential data exposed to anyone who knows a business name)
**Status:** FIXED — 2026-11-22. Generation fixed in both paths, all existing tokens rotated, test clients deleted. New links must be sent to every client (list held outside this repo).
**Found:** 2026-11-22, during an end-to-end test of the new marketing site's "Work with me" form, which registers clients through `portal_register_client`.
**Area:** Client portal access control (`/portal/:token`)

---

## Summary

A client's portal is reached at `portal.lonewolfdigitech.com/portal/{portalToken}`, and
that `portalToken` is the **only** thing protecting it — the portal is anonymous by
design and reads through `portal_snapshot(token)`. The problem is that the token is a
**slugified version of the client's business name**, not a random secret. Business names
are public, so the portal URL is trivially guessable.

Anyone who knows (or guesses) a client's name can open that client's full portal — active
projects, engagement value, outstanding balance, invoices, quotes and contracts — with no
login, from any browser.

## Impact

A portal snapshot exposes commercially sensitive data: project phases and deliverables,
quotation/engagement values, outstanding balances, invoices, and contract records. (File
*contents* are served through separate time-limited signed URLs, so those are not directly
listed here, but everything else on the dashboard is.) Because the token is derived from
the name, an attacker needs no leaked link — only the client's name, which is public.

There is also a lesser correctness risk: two clients whose names slugify the same way
collide on the `UNIQUE` token (the code suffixes `-2`, `-3`, … to work around it), which
makes some tokens even more guessable.

## How it was reproduced

1. Submitted the marketing site's contact form with business name
   `ZZ PROBE (delete me)`. The form called `portal_register_client`, which returned
   `{"ok": true, "name": "ZZ PROBE (delete me)", "portalToken": "zz-probe-delete-me"}`.
2. Opened `https://portal.lonewolfdigitech.com/portal/zz-probe-delete-me` in a clean
   browser with no session or login.
3. The full live client dashboard loaded (Overview, Progress, Invoices, Quotes, Files,
   Contracts) for that client.

The token `zz-probe-delete-me` is just `slugify("ZZ PROBE (delete me)")`.

## Root cause

The token is generated by slugifying the name in **both** registration paths:

- **Self-registration / the website** — the Supabase SQL function `portal_register_client`
  (not in the repo; it lives in the database). It returns a name-slug token, as the
  reproduction shows. Called from `src/pages/JoinClient.tsx` and by the marketing site.
- **Admin-created clients** — `src/store/StudioStore.tsx`, `createClient()` (around
  line 568), which does `const base = slugify(input.name)` and uses that as `portalToken`
  (`slugify` is defined at line 221).
- **Seed data** — `src/data/seed.ts` has name-slug tokens (`cakes-and-bakes`, `wyfix`,
  `greyview`, `metoo-foundation`).

The lookup side is fine and needs no change: `portal_snapshot(p_token)` (called from
`src/store/PortalStore.tsx:71`, route `/portal/:token` in
`src/pages/portal/PortalLayout.tsx`) is `SECURITY DEFINER` and filters by token
server-side. The weakness is purely that the token is predictable.

## Recommended fix

Generate a **random, unguessable** token everywhere a client is created, and keep it
`UNIQUE`. 128 bits of randomness, URL-safe, is plenty.

- **SQL `portal_register_client`** — set the token to, e.g.,
  `encode(gen_random_bytes(16), 'hex')` (pgcrypto) or
  `replace(gen_random_uuid()::text, '-', '')`, instead of slugifying the name. Return that
  token as now. This one change fixes the website too, since the site only uses whatever
  token the function returns — **no marketing-site change is needed.**
- **`StudioStore.tsx` `createClient()`** — replace the `slugify(input.name)` token with
  `crypto.randomUUID().replace(/-/g, '')` (or equivalent). The name-collision suffix loop
  can go; random tokens don't collide in practice (keep the `UNIQUE` constraint as a
  backstop).
- **`seed.ts`** — give the demo clients opaque tokens too, so the examples don't model the
  insecure pattern.

### Rollout / migration

Existing clients already have guessable name-slug tokens, so a fix for new clients isn't
enough on its own.

1. Write a migration that sets a fresh random token on **every existing client**.
2. This **invalidates every current portal link.** Each active client must be re-sent their
   new link (the portal link is the credential, so rotating it is the point — same idea as
   rotating the join code in Settings).
3. Confirm `portal_snapshot` still resolves a valid token and returns nothing for an
   invalid/guessed one (no code change expected there).

## Acceptance criteria
